NOTE: These values are not final and are subject to change
NOTE: Scaling factors should be powers of two to avoid floating point rounding during the calculations
NOTE: Floats can represent 24bit integers losslessly, so I can scale values to at least "max value = 2^24 = 16777216" and downscale them in context float providers unless I intend to use them in integer calculations.
NOTE: +-/* for floats that are scaled up by a power of two doesn't require dividing the individual numbers by their scaling factor first. Precision doesn't get lost.

Object:
- BlockPos: 1x
- PosWithinBlock: 16,777,216x (2^24. Max value of 1.0, so a scale of 2^24 works)
- LinearVelocity: 131,072x (2^17, so 7 bits for whole-block velocity, meaning a max velocity of 128 blocks, over 5 blocks per tick. Far more than I can handle anyway)
- AngularVelocity: 262,144x (2^18, so 6 bits for radians. Max 64 radians, or ~10 rotations per second. Supporting any more would be useless)
- Scale: 65,536x (2^16, so 8 bits for full blocks. Leaves opportunity for (static) objects spanning 256 blocks across. Inertia breaks way before that currently (2^14), but it's good to support for static objects)
- InverseMass: 268,435,456x (2^28)
   - Right now, it has small increments, and 268,000 tonnes is the largest possible mass before it becomes infinite. A lower scale would preserve more floating point accuracy when applying impulses.
- Orientation: 16,777,216x (2^24. Max value of 1.0, so a scale of 2^24 works)
- LinearVelocityFromAcceleration: 131,072x (2^17)
- AngularVelocityFromTorque: 262,144x (2^18)
- RotationMatrix: 16,777,216x (2^24. Max value of 1.0, so a scale of 2^24 works)
- SpecificInverseInertiaLocal: 262,144x (2^18. InverseInertiaTensorLocal without mass, necessary to avoid overflows or precision errors while storing)
- SpecificInverseInertiaWorld: 262,144x (2^18. InverseInertiaTensorWorld without mass, necessary to avoid overflows or precision errors while storing)
   - With this, it supports a max scale of ~32 and works for the min scale. Going higher would get close to overflowing, whereas going lower wouldn't do anything beneficial for my supported object scale.
   - I could also store it in 2 ints so I could actually store the inverse inertia tensor with the mass component.
- HalfExtentAxisProjections: 8,388,608x (2^23, so it supports objects of 256 size. Can't scale up more, because small inaccuracies could cause the value to barely overflow)
- AABB: 64x (2^6. World position, necessary for fast object-object AABB checks. If I need a more accurate one for terrain, that can be added later on.)
- AABBRelative: 65536x (2^16. 2^6 should be sufficient, but having the same scaling as "Ray.RelativePos" makes it faster, and some extra precision can't hurt.)
